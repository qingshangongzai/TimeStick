# Code Review

> 编码规则（核心原则、Rust/Win32 约定、零 panic 策略、验证约定等）以根目录《开发规范.md》为唯一真源；本 skill 只负责审查流程与产出格式，规则细节见《开发规范.md》，冲突时以它为准。

只读模式：只分析问题、给出结论，**不修改任何代码**。但允许（且建议）运行只读的验证命令——cargo check、cargo clippy、cargo build --release——用退出码与实际输出锚定"通过 / 失败 / 警告"等事实性结论，不要凭推断断言。

**实证原则（对抗幻觉）**：审查涉及 `windows` crate 的 API 签名或运行时行为（如 UpdateLayeredWindow 的参数语义、D2D 接口方法、消息时序）时，读实际源码（~/.cargo/registry 下的 windows-0.62 crate）或 docs.rs / 官方 Win32 文档验证，禁止凭记忆断言——windows crate 各版本差异大，记忆极易过时。框架内部行为无法从项目代码直接看出时，标注"据经验，未验证"或补一次源码确认。

## 审查流程

0. **排除 Git 忽略的文件**：被 .gitignore 忽略的文件（如 /target、.trae/、.zcode/、.git-diff.txt）不属于审查范围，即使对话中修改过，也**一律不审查、不出现在审查结果中**（下方 git 命令本身会排除它们，但基于对话上下文审查时也须遵守）。若本次改动全部属于被忽略文件，直接告知用户"改动均为 Git 忽略文件，不在审查范围内"。不确定某文件是否被忽略时，用 git check-ignore <路径> 验证。
1. **按变更复杂度分流**（与 commit-message-generator 的"简单/复杂修改"分流对齐）：
   - **简单变更（快速通道）**：常量数值调整（视觉参数、延迟时间）、注释、重命名等无逻辑改动的变更，且对话上下文已完整覆盖改动内容与意图（如改动由本轮对话产生）时，跳过步骤 2-5，**不执行任何 git 命令**，直接基于对话上下文审查；维度精简为「规范合规」（命名/双语分层/常量定义方式）、「无效修改」、关联一致性（使用该常量的所有点语义是否同步变化）；对存疑点直接 Read 源文件核实后再下结论
   - **复杂变更（完整流程）**：涉及新逻辑、重构、新增模块/消息/线程、跨模块联动，或对话上下文不足以确信完整覆盖改动时，执行步骤 2-5
2. 执行 `[Console]::OutputEncoding = [Text.Encoding]::UTF8; git -c core.quotepath=false diff HEAD --no-color --output=.git-diff.txt`，将暂存+未暂存的所有变更输出到项目根目录的临时 txt 文件（--output 绕过 PowerShell 管道避免 LF 行尾截断与编码损坏，**禁止用 > 重定向替代**——PowerShell 会写成 UTF-16；--no-color 去除 ANSI 转义码；-c core.quotepath=false 防止中文路径被转义成八进制序列——本项目位于中文目录下，必加；git diff HEAD 一条命令覆盖两种状态，不会产生空文件）；用户指定文件则直接读全量
3. 执行 `[Console]::OutputEncoding = [Text.Encoding]::UTF8; git -c core.quotepath=false ls-files --others --exclude-standard` 列出未跟踪的新文件（输出量小，直接读终端输出即可，无需落盘；可与步骤 2 用分号合并为一条命令）——git diff HEAD **不含 untracked 文件**，会漏审新建的模块/脚本/文档；对列出的每个文件用 Read 工具读取全量内容一并审查
4. 使用 Read 工具读取 .git-diff.txt，获取已跟踪文件的变更；阅读变更区域前后各 20 行上下文，理解改动意图；**报告行号时以 @@ 段头标注的起始行为基准换算回源文件真实行号**，不要直接使用 diff 内的相对位置；对将写入报告的 🔴/🟡 项，落报告前回读源文件对应区域确认真实行号（@@ 换算本身易错，行号作为修复依据时尤须确认）
5. 生成审查结果后，删除 .git-diff.txt（已在 .gitignore 中；若上次审查中断残留，本次开始前先清理）
6. 运行只读验证命令（cargo check 必跑；涉及较大改动时补 cargo clippy），把编译器/linter 警告（dead_code、unused 等）作为「冗余代码」维度的实证来源
7. 按下方维度审查，判定标准读《开发规范.md》对应节
8. 仅输出有问题项，全通过输出"✅ 未发现问题"

## 审查维度

> 🔴 必须修复 | 🟡 建议优化。每维度的判定标准以《开发规范.md》为准，下表只标"看什么"与出处。

| # | 维度 | 看什么 | 出处 |
|---|------|--------|------|
| 1 | 过度设计 🔴 | 当前不需要的抽象/复杂度 | 核心原则第 1 条 |
| 2 | 冗余代码 🔴 | 定义了但未使用的代码（dead_code warning 为实证） | 核心原则第 2 条 |
| 3 | 无效修改 🟡 | 不产生实际效果的改动 | 核心原则第 3 条 |
| 4 | 复杂逻辑 🟡 | 可读性差或过度复杂 | 核心原则第 4 条 |
| 5 | 过度防御 🟡 | 针对"不可能发生"场景的防御 | 核心原则第 5 条 |
| 6 | 命名清晰 🟡 | 名称表达意图、风格与既有命名一致 | 核心原则第 6 条 |
| 7 | 规范合规 🔴 | 错误三级制、零 panic、unsafe 组织、双语分层、消息/线程约定 | 「Rust 编码规范」「Win32 / 渲染规范」节 |
| 8 | 验证完整性 🔴 | 逻辑层改动是否附测试/验证脚本 | 「验证与测试」节 |

**审查补充**（《开发规范.md》未逐条展开、审查时需知道）：

- 新增 `unwrap()` / `expect()` 一律 🔴（零 panic 策略，豁免情形见规范 4.3）
- 新增 `unsafe impl Send/Sync` 一律 🔴（用 usize 中转，见 detect.rs 模式）
- 新增可变状态被后台线程访问、或 WndProc 未判空取 userdata，一律 🔴（线程模型违约）
- 每处非显然 unsafe 须有中文注释说明理由，缺失为 🟡
- render.rs 矢量几何坐标、亮度阈值 128 等既有豁免魔法数字不算违规（见核心原则第 4 条例外清单）

## 审查范围

覆盖 `src/*.rs` 与 `build.rs`。`installer.nsi`、`scripts/` 只检查明显错误（路径、版本号来源），不深入审查。方案文档（过程性文档/）不审内容，只审与代码的一致性。

## 输出格式

| # | 文件:行号 | 严重度 | 维度 | 问题描述 |
|---|----------|--------|------|---------|
| 1 | src/floater.rs:135 | 🔴 | 规范合规 | 新增 unwrap 无不变量保证，违反零 panic 策略 |
| 2 | src/render.rs:88 | 🟡 | 复杂逻辑 | draw_buttons 超 100 行，矢量绘制建议拆分 |

- 每项附 1-2 句修复建议
- 🔴 必须修复项排在前面，🟡 建议优化项排在后面
- 若某维度无问题，不输出该维度
